1. Executive summary

The goal is not one giant “HR table” or a screen where an administrator can arbitrarily change every database field. The goal is a controlled organization platform: super admins define the organization and its supported modules, assign people and access, configure safe business models and workflows, and review an immutable record of important actions.

One identityProfile/login is separate from employment, reporter, or vendor relationships.
One policy engineAccess is enforced by database permissions and server routes, not only hidden UI.
One governed platformNative product modules and custom models share audit, ownership, and lifecycle rules.
Recommended delivery shape: finish and verify the organization foundation first; then integrate existing newsroom and HR operations; then add genuinely new business modules only when their requirements are approved. Do not label payroll, recruitment, attendance, or accounting “complete” just because their module names appear in a catalog.

What this document is

A proposed, testable implementation baseline for one organization, built around the existing Chowk portal.

What it is not

It is not proof that the current code/database is production-ready, and it is not approval for payroll, legal, or privacy policy.

How to use it

Business owners approve the decision baseline; engineering turns the requirements and acceptance evidence into milestones and tests.

Start with Section 16 for proposed decisions. If a default is not accepted, record the alternative and its impact before building that part of the system.

Recommended v1 scope: organization setup, access, employee HR lifecycle and policies, safe custom models, workflow foundation, and integration of the existing newsroom/reporting domains. AI is an optional, separately gated assistant capability: start with a small newsroom pilot and low-risk internal knowledge assistance; never use it as an autonomous decision-maker. New modules such as payroll remain separately scoped.

The current application is a Node.js portal using Supabase Auth, PostgREST, PostgreSQL, RLS/security-definer functions, and additive SQL migrations. Current local work has added employee/HR foundations, configurable record models, organization settings/modules/roles, and a generic workflow runtime. These are development changes, not proof of a deployed or fully tested production system.

3. Architecture principles and operating rules

Clear domain ownership

Employment records belong to HR; reporter credentials and coverage belong to newsroom operations; an account/profile represents identity. The same person may have multiple relationships without duplicate login identities.

Configuration is bounded

Admins configure supported entities, fields, access, and transitions. They do not execute arbitrary SQL, create unsafe code, or override platform-level invariants from a form.

Fail closed

Unknown permission, disabled module, inactive role, or invalid lifecycle transition denies the operation. User-facing errors explain what action is needed; server logs preserve diagnostic detail.

Audit before convenience

Capture actor, target, time, reason, old/new values where safe, request/correlation ID, and revision for access, lifecycle, settings, workflow, and sensitive-data changes.

Version configuration

Published policies and workflow/model configurations are versioned. New rules should not rewrite the historical basis for a prior approval or employee acceptance.

Delete with retention awareness

Prefer deactivate, archive, or end-date. Hard deletion is limited to unused drafts or legally approved erasure; preserve audit records and referential integrity.

Recommended scope: deliver a single-organization application with an explicit organization ID on organization-owned records and strict organization scoping in all queries. This gives clean boundaries and a possible future path to multi-tenant SaaS, without pretending that one deployment is already a tested multi-tenant product.

6. Data architecture and naming contract

6.1 Core relational model

organizations ├─ organization_settings → setting revisions / events ├─ hr_departments → hr_positions ├─ profiles (auth identity) │ └─ organization_people (relationship + organization scope) │ ├─ access_role_id → organization_access_roles │ │ └─ role_permissions → permission_catalog │ └─ relationship lifecycle / source reference ├─ hr_employees (profile-linked employment record) │ ├─ hr_employee_assignments → department, position, manager, access role │ ├─ hr_policy_documents → immutable policy versions │ └─ hr_policy_acceptances → employee + exact version + timestamp ├─ organization_module_catalog → organization_modules → config versions ├─ organization_models → fields, permissions, transitions │ └─ organization_records → revisions / immutable events └─ organization_workflows → states, transitions └─ workflow_instances → events + approval requests

6.2 Naming and identity rules

  • Use stable UUID primary keys for domain rows; use readable employee numbers and reporter IDs as unique display/business identifiers, not foreign keys.
  • Use `employee_id` for the HR person reference and `manager_employee_id` for a manager relationship. Do not call employee rows “staff”. Existing newsroom “staff” tables must be migrated deliberately, not renamed blindly.
  • Use `profile_id`/`person_id` for account identity references where the concept is a person, `organization_id` on organization-owned records, and explicit source type/ID for traceable synchronization.
  • Keep department, position, access role, permission, and employment status as distinct fields/concepts.
  • Use immutable or append-only event tables for policy acceptance, access changes, approval decisions, and important configuration revisions.
  • Use `created_at`, `updated_at`, `created_by`, `updated_by`, `starts_at`, `ends_at`, and explicit lifecycle status consistently. Enforce valid status/date combinations with constraints or transaction functions.
  • Use database constraints and unique indexes for rules that must remain true under concurrent requests. Do not rely on browser validation.

6.3 Custom-model safety envelope

Admin-defined models should use metadata plus typed JSON records only inside an explicit product envelope: allowed field types, field-count and payload-size limits, required/indexed fields, permitted reference types, field visibility, validation rules, export behavior, retention, versioning, and role-scoped CRUD. Reject executable expressions, arbitrary SQL, unsafe HTML, and references that cross organization boundaries. Native employee, payroll, reporter, and article records remain native relational domains where integrity or law requires them.

7. Identity, access control, and role assignment

7.1 Authorization decision

An access decision is based on the authenticated actor, active organization relationship, active role and grant, module state, requested action, target record, and scope. Every layer must agree.

allow(actor, action, resource) = authenticated(actor) AND relationship_is_active(actor, resource.organization_id) AND module_is_enabled(resource.module) AND role_is_active(actor, resource.module) AND permission_is_active(action) AND grant_contains(role, action) AND scope_matches(actor, resource, action) AND lifecycle_transition_is_valid(resource, action)

7.3 Super-admin controls and guardrails

  • Bootstrap one verified super-admin through a controlled server-side procedure; require MFA, strong recovery, and a documented break-glass process.
  • Super admin can configure organization identity, structure, modules, access role catalog, permission assignments, policies, and supported workflows.
  • Do not allow removal/deactivation of the last active super-admin without first promoting and verifying a replacement.
  • Role changes affecting the acting user, service accounts, or privileged accounts should require step-up authentication and an audit reason.
  • Use least privilege for ordinary administrators. “Admin dashboard access” must not silently mean “all personal data access”.
  • Access assignment must not exceed the actor's delegation authority except for the protected super-admin operation. Log both requested and effective grants.
  • On termination/suspension, revoke sessions/tokens where supported, disable relationships and assignments, remove access grants, preserve records, and notify owners.
Permission labels and route middleware are not enough. Verify authorization in server routes, security-definer database functions, row-level policies, storage policies, scheduled jobs, and direct PostgREST access.

8. End-to-end workflows

8.1 Initial organization bootstrap

Provision project and secure secrets→Reconcile schema and migration history→Create organization root→Verify super-admin→Run setup checklist→Publish baseline
  1. Provision a staging Supabase project and application environment; confirm backups, auth email configuration, storage bucket policies, and secret management.
  2. Inspect the actual schema, applied migrations, existing profiles, staff/reporter records, triggers, RLS policies, and storage objects. Produce a reviewed migration/backfill plan.
  3. Create the organization identity, primary locale/timezone/currency, legal-contact profile, and default configuration revision. Verify legal values rather than using demo defaults.
  4. Promote/verify the initial super-admin through the bootstrap command; enforce MFA/recovery and record the bootstrap event.
  5. Complete setup checklist: organization profile, departments/positions, access roles, enabled modules, policies, notification channels, retention, and first admin review.
  6. Publish configuration only after required settings validate. Keep an export/snapshot and change log for the initial version.

Failure path: setup is resumable and idempotent. A partial setup shows exactly which prerequisites remain; it must not create duplicate organizations or silently elevate the first ordinary signup.

8.2 Configure structure and management

Create department tree→Define positions→Map permissions to roles→Assign accountable owners→Validate module readiness
  1. Create top-level departments, then child teams; prevent cycles, invalid parents, and deleting a department with active dependencies.
  2. Define positions with clear title, department applicability, job description, and effective status. A position is not a permission.
  3. Define access roles by responsibility; attach only supported permission keys and allowed scope. Show a “who can do what” preview before saving.
  4. Assign module owners and workflow approvers. Require a second approver for selected high-impact changes if the organization chooses separation of duties.
  5. Run a readiness check for orphaned roles, unassigned permissions, missing owners, inactive modules, and unresolved workflow configurations.

8.3 Employee lifecycle

Authorized invitation→Identity verified→Preboarding→Assignment and access→Policy acknowledgement→Active employment→Change, suspend, or exit
  1. HR creates an employee invitation with approved email, employment type, planned start date, manager, department, position, and proposed access role.
  2. Invitee verifies identity using the controlled invite flow and sets credentials. The account profile and HR employee relationship remain separate records with linked IDs.
  3. Employee enters preboarding; the system provisions only the minimum required access. No privileged role is activated merely because an invite was accepted.
  4. HR completes required fields, assignments, equipment/access checklist where implemented, and assigns policy versions. The employee reads and accepts the exact published version; record immutable evidence.
  5. Authorized manager/HR approves activation. System checks all requirements transactionally, creates effective assignment, enables the role, and records the actor and timestamp.
  6. For transfer/promotion, close the previous assignment with a reason and date; add the new assignment; recalculate access; preserve historical snapshots.
  7. For suspension or termination, set effective dates, revoke access, cancel outstanding sessions/invitations, hand off approvals, retain lawful records, and produce an offboarding audit packet.

8.4 Reporter / external newsroom collaborator lifecycle

Application or invitation→Review and verification→Agreement issued→Exact version accepted→Credentials and coverage→Renew, suspend, or revoke
  1. Applicant creates an account/application; intake validates required fields, consent/accuracy declaration, allowed masked documents, and preferred coverage. Submission is not reporter approval.
  2. Reporter operations reviews identity, documents, qualifications, conflicts, and coverage; each request-for-information, resubmission, rejection, or approval has an actor, reason, and history.
  3. After approval, authorized admin verifies the organization's legal profile, generates the exact service-agreement version, previews it, and issues it through a private, expiring delivery channel.
  4. Applicant accepts the exact issued PDF/version; hash, version, actor, and timestamp are recorded. Credentials are not issued before the required agreement/authority steps complete.
  5. Admin issues a unique reporter credential/ID, activates the reporter relationship, and assigns valid coverage. Coverage must be active in the location hierarchy and effective dates may not overlap improperly.
  6. Renewal or change requires explicit new assignment/agreement version as policy requires. Expiry, suspension, termination, or application deletion revokes access and credentials while preserving required evidence.
  7. Editors/moderators/publishers are newsroom collaborator relationships. They receive only the access role needed for the job; do not silently create an employee record unless a separate employment process says so.

Failure paths: missing/invalid documents return the application to a named state with an applicant-visible request; agreement delivery failure retries without marking acceptance; coverage conflict blocks credential activation; revocation blocks the next protected operation.

8.4a Article editorial lifecycle

Draft by reporter/editor→Submit + coverage check→Moderator review→Editor review→Schedule / publish→Correct / archive
  • Draft: author creates/edits within assigned coverage and required fields. Each edit creates a revision; media/category/location references must be active and authorized.
  • Submit: verify minimum content, reporter status/credential, active assignment, coverage, category, location, and module state. Submission records timestamp and routes to the eligible queue.
  • Moderator: assigned moderator may start review, request changes, reject with reason, or send to editor. Assignment/coverage rules are rechecked at action time.
  • Editor/publisher: review, return with reason, schedule for a future time, publish, unschedule, or archive according to the permission key and allowed current state.
  • Scheduled job: immediately before publishing, re-check article revision/state, module, category/location status, author/approvals, and scheduled time. Job is idempotent and emits an immutable event.
  • Correction after publication: create a new revision and correction reason; retain the prior published version and record who authorized the correction. Never silently replace the audit history.

Failure paths: stale revision returns conflict and reload; invalid coverage blocks submit/review; publisher/job outage preserves scheduled state and retries; a disabled newsroom pauses publication; public read policy only exposes currently published and enabled content.

8.4b Access to a record under review (owner and delegation)

Every review item has one accountable owner or queue plus a permissible coverage/department scope. A manager may delegate only to an active, eligible user for a bounded date range. Delegation records grantor, delegate, resource scope, reason, expiry, and revocation. Delegation cannot transfer super-admin, unrestricted export, or legal-hold authority. On leave/termination, unowned items enter a visible reassignment queue; no silent reassignment grants broader access.

8.5 Admin-configured management model

Choose supported model type→Define fields and validation→Set access and scope→Define transitions/approvals→Preview and test→Publish version→Operate and audit
  1. Admin creates a model such as Travel Request, names its owner, retention policy, and sensitivity classification.
  2. Select allowed fields (text, number, date, boolean, single/multi choice, approved relationship, attachment reference); define required, length/range, uniqueness, and visibility rules.
  3. Define list/read/create/update/archive permissions per role and scope; define field-level visibility for sensitive values where required.
  4. Define valid states, transitions, transition permissions, required reason, approver count, and any SLA/reminder. No free-form executable expressions.
  5. Preview create/edit/list screens; run validation examples; show the effective permission matrix; require a publish confirmation and version increment.
  6. Records reference the published model version, keep revisions and state events, and obey organization boundaries. Model changes cannot corrupt old record history.
  7. Retire a model only after reviewing active records, integrations, exports, workflow approvals, and retention. Archive rather than cascade-delete used data.

8.6 Workflow and approval lifecycle

Start with valid subject→Initial state→Authorized transition→Approval pending, if configured→Decision and revision check→State change + immutable event→Notification/outbox
  • The current generic runtime stores a format-validated subject type and ID as text; it does not resolve or bind them to authoritative domain records. Starts, transitions, and approval decisions are blocked for newsroom, reporter, agreement, and HR modules until a foreign key or validated domain adapter exists. Other generic instances are non-authoritative tracking, not enforcement for critical records.
  • At transition, lock or compare expected revision; validate current state, target state, permission, scope, module, required reason, and approval policy in one transaction.
  • Approval requests are unique per pending action, assigned to eligible approvers, expire or become stale safely, and cannot be approved by the requester where separation is required.
  • Write the state change and immutable audit event atomically. Use an outbox for notifications so delivery failure does not roll back an approved business action.
  • Do not let generic workflow configuration bypass hard domain invariants such as reporter credential requirements, employment termination controls, or article publication validation.

8.7 Deletion, correction, and records handling

  • Unused drafts: hard-delete only when no dependent record, acceptance, approval, or audit retention rule applies.
  • Used departments, positions, roles, models, policies, and modules: deactivate/retire; preserve references and history.
  • Employee/reporting relationships: end-date with reason; do not delete the person's identity to remove access.
  • Personal data correction: update the authoritative field, record actor/reason, preserve legally required evidence, and avoid copying sensitive values into general audit logs.
  • Legal erasure requests: route through a documented privacy process with retention/legal-hold checks, controlled anonymization, and proof of completion.

8.8 Access request, approval, and periodic review

Request access with purpose and expiry→Manager validates job need→Data/module owner approves scope→System checks delegation and conflicts→Grant with expiry + audit→Quarterly recertification→Revoke or renew
  1. Employee or manager requests a named role/permission, scope, business purpose, start date, and end date; requests cannot be for arbitrary permissions outside the catalog.
  2. Manager confirms job need. The protected data/module owner confirms the requested scope. High-impact grants follow the second-person rule in D-09.
  3. The system rejects inactive users, disabled modules, invalid departments, self-approval, privilege escalation by an unauthorized delegator, and grants without an expiry where policy requires one.
  4. On approval, write the grant and immutable event atomically; notify requester and owner. Grant becomes effective at the approved time and expires automatically.
  5. At least quarterly, each manager/module owner reviews a roster of active grants with last-used time and relationship/assignment status. Decisions are renew, narrow, revoke, or investigate.
  6. Unreviewed high-risk grants are not silently left active: escalate to owner; after the configured grace period (proposed: 14 days), suspend the grant and notify the user.

Evidence: request, business purpose, requester, approvers, permission/scope, effective/expiry time, before/after grant, notification outcome, and review decision. Failure to notify does not undo a valid grant; the outbox retries and alerts the owner.

8.9 Department, position, or manager change

Propose change + effective date→Impact preview→Owner approval→Close old assignment→Create new assignment→Recompute access→Notify affected owners
  1. Authorized HR user selects person, new department/position/manager, effective time, reason, and whether access should change.
  2. Preview reports direct and inherited department scope effects, current/pending approvals, record ownership, manager delegation, policy applicability, and grants that will be gained/lost.
  3. Validate the manager is active and not the employee; validate the department tree has no cycle; reject overlapping primary assignments and invalid effective dates.
  4. At the effective timestamp, close the prior assignment and create the new version without erasing history. Recompute grants using the approved assignment model.
  5. Reassign approval queues and owned records explicitly; do not silently transfer confidential records. Notify employee, old/new manager, HR, and module owners as applicable.

Failure path: transaction rolls back if assignment or grant recalculation fails. If an external notification fails after commit, retain the committed assignment and retry notification through the outbox.

8.10 Module readiness, enablement, disablement, and resume

Module planned→Owner + controls assigned→Readiness evidence passes→Super-admin requests enable→Second approval if required→Enable and smoke-test
  1. Module owner supplies implemented version, dependencies, permissions, data classification, retention, support contact, readiness tests, and operational runbook.
  2. System shows readiness separately from the desired enabled flag. Block enablement when code version, required migration, dependency, owner, or acceptance evidence is missing.
  3. Before enablement, preview affected routes, existing data, jobs, roles, and public surfaces. Confirm configuration validation and owner sign-off.
  4. On disablement, block ordinary reads/writes according to D-11, pause jobs/approvals, retain records, emit an audit event, and alert the module owner. Security/administrative alerts continue.
  5. To resume, verify code/schema version, data integrity, pending queues, deadlines, external integrations, and overdue scheduled actions. Require an explicit resume preview; do not auto-run stale work.

Emergency disable: a super-admin may immediately disable a module for active risk. It records a reason, alerts security and the module owner, and opens an incident review. Re-enable requires a second approver and a documented corrective action.

8.11 Policy drafting, review, publication, and acknowledgement

Owner drafts→HR/legal review→Applicability and impact check→Publish immutable version→Notify affected people→Collect exact-version acceptance→Escalate overdue cases
  1. Policy owner creates a draft with purpose, effective date, owner, audience selector, acknowledgement requirement, renewal trigger, and prior-version relationship.
  2. HR/legal reviewer approves content and retention basis. A policy cannot be published with placeholder legal/company details or an empty audience.
  3. Before publish, preview who is included/excluded, who will be re-prompted, and what workflows/actions will be blocked if acknowledgement is mandatory.
  4. Publish creates an immutable version and content hash. Notify affected employees through the outbox; keep delivery state separate from acceptance state.
  5. Employee accepts the exact version while authenticated; record version/hash, actor, time, and evidence. A newer version creates a new requirement only for its configured audience.
  6. Overdue acknowledgement escalates to manager/HR after configured intervals. Block only explicitly named actions (proposed default: sensitive HR self-service or activation readiness), not unrelated public/newsroom access.

8.12 Account recovery, suspected compromise, and security incident

Detect or receive report→Open incident + severity→Contain account/module/session→Preserve evidence→Investigate and notify owners→Recover safely→Post-incident review
  1. Reporter or monitoring creates an incident record with reporter, time, affected identity/module/data, evidence references, and a severity. Proposed levels: Sev-1 active sensitive-data exposure/service-wide compromise; Sev-2 privileged account compromise or major module outage; Sev-3 contained single-user issue; Sev-4 request/minor defect.
  2. On-call security owner acknowledges proposed Sev-1/2 within 30 minutes during declared coverage hours; outside those hours, publish the actual support coverage and response commitment before launch.
  3. Contain by revoking sessions, suspending affected relationship, rotating compromised secrets, pausing risky integrations/module, or restricting access. Record every emergency action and actor.
  4. Preserve audit/log evidence with restricted access and chain-of-custody metadata. Do not copy passwords, tokens, or sensitive document contents into incident comments.
  5. Recovery uses independently verified identity, reissued credentials/MFA, reviewed permissions, and a test of affected business functions. Restore access minimally; do not re-enable old grants automatically.
  6. Security/privacy/legal owner determines notification obligations. Close incident only with root cause, impact, remediation, residual risk, and follow-up owner/date.

Account recovery: use the identity provider's verified recovery process. A super-admin must never set/read a user's password or bypass identity verification. Break-glass access is separate, time-bounded, alerted, and reviewed next business day.

8.13 Sensitive-data access, export, correction, and erasure

Authenticated subject or authorized requester→Verify identity and authority→Privacy owner classifies request→Check scope, retention, legal hold→Approve minimal action→Execute + verify→Record outcome
  1. Create a tracked request with request type (access, correction, export, deletion/restriction), identity verification result, jurisdiction, due date, and assigned privacy owner.
  2. Locate data across profile, HR, reporter, media/document storage, audit, exports, and backups using a controlled inventory. Do not expose unrelated people's data.
  3. Check statutory/business retention and legal holds. Legal/privacy owner decides whether to provide, correct, restrict, anonymize, or reject a requested deletion and records the basis.
  4. Generate exports as encrypted, expiring, audited jobs with recipient verification and download limits. Never place sensitive exports in public storage or ordinary email attachments.
  5. Execute corrections/deletion as a staged job; preserve only permitted evidence, references, and audit. Verify the result and record exceptions and affected systems.
  6. Close only after requester communication and owner review. Backup expiry behavior and third-party processor deletion are recorded in the request.

8.14 Notification, scheduled action, and background-job failure

Business transaction commits→Outbox event stored atomically→Worker claims idempotently→Retry with backoff→Deliver or dead-letter→Alert owner and reconcile
  • Business record and outbox event commit together. Worker delivery never determines whether an already-committed approval or assignment is valid.
  • Every job has an idempotency key, bounded attempts, exponential backoff with jitter, visibility timeout/lease, and dead-letter state. Reprocessing must not duplicate credentials, payments, approvals, or publication.
  • For expired/invalid recipients, mark permanent failure and create an owner task. For provider outage, retry and alert after threshold. Never silently discard.
  • Scheduled publication and lifecycle jobs re-check module state, record revision, current authorization/policy, and scheduled time immediately before execution.
  • Operators can pause/replay a job only with permission and reason; replay is audited and safe to run more than once.

8.15 Recovery from failed release or data migration

Detect failed post-check→Stop writes / declare incident→Choose rollback or forward fix→Restore or reconcile snapshot→Validate counts and critical flows→Owner go/no-go
  1. Each release names objective stop conditions (integrity mismatch, elevated 5xx/authorization errors, unavailable sign-in, unsafe data exposure) and an incident commander.
  2. Prefer feature-flag disable or forward fix for additive changes. Restore a backup only under the data-loss decision and RPO policy; a database restore can discard valid writes after the snapshot.
  3. After restore/fix, compare migration version, record counts/checksums, relationship mappings, grants, storage references, scheduled work, and audit continuity.
  4. Resume writes only after technical lead, database operator, affected domain owner, and incident commander approve the go/no-go checklist.
  5. Publish user impact and next update; preserve incident evidence and complete root-cause review within five business days (proposed target).

8.17 Controlled people/data import

Choose approved template→Upload to private staging area→Validate and match identities→Preview changes and errors→Owner approves batch→Commit idempotently→Reconcile and remove source file
  1. Import operator selects a versioned template and authorized relationship type. Do not mix employee, reporter, and general contact imports in one untyped file.
  2. File is uploaded privately, encrypted in transit/at rest as supported, size-limited, malware-scanned where available, and assigned an import batch ID. Raw files are never placed in public buckets or ordinary logs.
  3. Dry-run validates columns, formats, required fields, duplicate emails/IDs, department/position keys, manager references, status-date combinations, and proposed access changes. Matching an existing identity requires verified stable identifiers, not name similarity.
  4. Preview reports inserts, updates, rejected rows, duplicate candidates, and calculated access deltas. Sensitive values are masked. A business owner resolves each conflict; no silent “last row wins”.
  5. Authorized data owner approves the exact preview checksum/count. Commit uses idempotency keys and row-level transactions; a failed batch can resume without duplicating profiles or assignments.
  6. Post-import reconciliation compares source/accepted/rejected counts and sampled references, tests representative sign-in/permissions, and records the final report and approver.
  7. Delete or quarantine the source file and temporary exports according to the approved retention schedule. Preserve only the minimal restricted batch manifest required for audit.

Default: imported accounts do not receive privileged access automatically. Role grants are a separately reviewed part of the batch and must pass the same delegation and high-impact approval checks as manual grants.

13. Definition of “complete” and release acceptance

The platform is ready for production only when the following conditions are demonstrated in staging with representative identities and documented owner sign-off:

  • A super-admin can bootstrap and configure organization identity, structure, access roles, module state, policy versions, models, and workflow rules without direct SQL.
  • Database and server enforce the same authorization; API/RPC/PostgREST/storage paths are tested for both allowed and denied access.
  • A custom role grants exactly the selected action and scope; removing a grant/module blocks the next request, not just the next page render.
  • Employee onboarding, policy acknowledgment, transfer, suspension, and termination work end-to-end; termination removes access and preserves the audit trail.
  • Reporter and newsroom collaborator lifecycles remain separate from employment; coverage and editorial invariants are preserved.
  • Configuration and record changes have immutable history, revision conflict handling, validated deletion/archive behavior, and meaningful error reporting.
  • Workflow approval cannot be self-approved where prohibited; stale/duplicate requests are safe; state and audit write atomically.
  • Disabled modules deny relevant server/database operations and are clearly disclosed in the UI.
  • Backups can be restored; migration rehearsal, alerting, rate/error monitoring, secret handling, and support ownership are documented.
  • Optional modules not implemented are visibly marked “not available” and cannot be enabled as though functional.
  • If AI is enabled, authorized-source checks, data minimization, user-visible draft labeling, provenance, human confirmation, provider failure handling, usage limits, and the per-use-case kill switch pass tests; no AI path can bypass ordinary permissions or commit a consequential action.
Test matrix: super-admin, ordinary admin, HR manager, department manager, employee, reporter, moderator/editor, subscriber, disabled user, and anonymous visitor × read/create/update/archive/ transition/approve/export × own/assigned/department/organization scope × module enabled/disabled.

18.3 Configuration, module, and custom-record lifecycle

  • Configuration: draft → validated → pending approval if high-impact → published revision → retired. Published revisions are immutable. Rollback means publish a new revision restoring prior values, never mutate history.
  • Module: planned → available after readiness gates → enabled → disabled/paused → enabled after resume checks, or retired. `planned` and `retired` cannot be enabled. Required core module cannot be disabled through ordinary settings.
  • Model definition: draft → validation errors resolved → preview tested → published version → retired. A published version is immutable; records remain attached to the version that defined them.
  • Record: model-specific controlled states. Every transition is a configured edge and must also pass the domain's non-configurable constraints. Archive is the default removal action.
  • Approval: pending → approved/rejected/stale/cancelled. Exactly one terminal decision; compare expected revision; requester cannot approve own high-impact request; decision and resulting state change are atomic.

19.3 API behavior contract

  • Keep the current same-origin Node API convention for browser-facing organization APIs. Use consistent resource routes under `/api/admin/organization`, `/api/admin/hr`, `/api/employee`, and `/api/organization`; version breaking public contracts deliberately.
  • Mutations require authenticated session, same-origin/CSRF validation, idempotency key for invitation/export/workflow start where duplicate execution is harmful, and a reason for privileged changes.
  • The acting user and organization scope come from the verified session and database context—not from an untrusted JSON field. If a target ID is supplied, the database must prove it belongs to that organization.
  • Use JSON response envelopes consistently: success returns `{ success: true, data, revision? }`; failure returns `{ success: false, error: { code, message, request_id, details? } }`. Never return SQL, stack traces, secrets, or sensitive before/after values to the browser.
  • Use HTTP 400 for malformed input, 401 unauthenticated, 403 unauthorized, 404 absent/inaccessible resource where disclosure is unsafe, 409 stale revision/conflict, 422 valid shape but invalid business transition, 429 rate limit, and 5xx for unexpected service failures.
  • Validate request body size, UUIDs, enums, dates, numeric bounds, JSON schema, uploaded content signature, and pagination limits at the server; repeat essential checks in database constraints/functions.
  • Paginate list APIs with stable ordering and bounded page size. Exports are separate audited jobs, not unlimited table responses.

19.4 Database invariants and transaction boundary

  • Every organization-owned row has a non-null `organization_id` and composite relationships/FKs where needed to prevent cross-organization joins.
  • Use unique constraints scoped to organization for keys, exactly one active primary organization for this deployment, checks for lifecycle/date consistency, and partial unique indexes for one current primary employee assignment.
  • Each mutation function derives `actor_id` from the authenticated database context; service workers use explicitly named service identities and record the triggering job/event.
  • Authorization, validation, current revision comparison, primary-row update, audit event, and approval state change happen in one database transaction where they form one business action.
  • All `SECURITY DEFINER` functions must set a safe fixed `search_path`, use schema-qualified objects, have minimum grants, and be reviewed for unintended public/anon execution. Revoke default execution explicitly.
  • Use transaction locks or optimistic revisions for competing transitions. A conflict returns 409 and forces a reload; never silently overwrite.

19.5 Audit and observability fields

Every security-relevant event records: event UUID, organization, authenticated actor (or controlled worker identity), action key, target type/ID, UTC timestamp, request/correlation ID, outcome, reason, revision, source channel, and a minimal redacted before/after diff. Do not store passwords, tokens, full bank/identity documents, raw secret values, or unnecessary IP/user-agent data in the audit stream.

19.6 Optional AI service contract

  • All model access goes through a server-side provider adapter/gateway. Keep API keys in the deployment secret manager; the browser never receives provider credentials. Pin and record provider/model/config versions and support controlled updates.
  • Before every call, enforce the active user session, use-case permission, module state, source-record permission, and purpose. Retrieve only authorized records and only the fields needed for that task; re-check access when a draft is saved. AI cannot widen user access.
  • Approve provider/subprocessor, deployment region, retention, training/no-training setting, security terms, and transfer/legal basis before sending organization content. Treat provider input/output as external processing. Use public/synthetic data for development and evaluation unless separately approved.
  • Retrieved text and user-uploaded content are untrusted: defend against prompt injection, poisoned instructions, cross-user retrieval, unsafe links, and output-as-code. Do not execute model instructions or expose hidden prompts/secrets. Outputs are escaped and schema-validated before display or use.
  • Models produce suggestions only. No function/tool calling with write, approval, role, export, delete, send, or arbitrary query capability. Any AI-generated artifact is an ordinary editable draft and must pass existing human approval and domain validation.
  • Log minimal provenance and operational metadata, not raw prompt/output by default. Keep approved retention, access, deletion, and subject-request behavior aligned with source data. Provider-side retention and training controls must be verified, not assumed.
  • Per-use-case controls include feature flag/kill switch, allowlisted users/data sources, input/output token and request limits, concurrency/rate limits, budget alert/cap, timeout, provider-health alert, and a manual fallback. Provider failure must not block core business operations.
  • Evaluate representative and adversarial examples before launch and after material model/prompt/retrieval changes. Track factual/source attribution errors, unsafe or biased outputs, reviewer edits/rejections, latency, failures, and spend; pause expansion when a release threshold fails.

22. Delivery controls, migration procedure, and release checklist

22.1 Migration and data reconciliation procedure

  1. Inventory: capture database migration ledger, table/column/FK/index/trigger/function/policy definitions, storage buckets/policies, row counts, and sampled anonymized records from the actual target.
  2. Classify sources: identify profile accounts, employees, staff-role assignments, reporters, applications, agreements, coverage, articles, and existing audit history. Name an owner for each source and target mapping.
  3. Define deterministic mapping: map source IDs to target IDs; resolve duplicates only with verified identity evidence. Never infer employee status from a newsroom role. Keep a source-to-target mapping table and preserve original identifiers in a restricted migration record.
  4. Dry run: run migration on a restored copy; produce counts by source/target/status, invalid rows, duplicate candidates, nulls, and predicted access changes. No destructive update in this pass.
  5. Review exceptions: business owner resolves each unmatched/ambiguous record. Document accepted exclusions and privacy-safe handling of source files.
  6. Rehearse upgrade: apply exact migrations and data backfill in order, verify constraints, triggers, grants, RLS, storage access, and application compatibility; test recovery from a snapshot.
  7. Approve cutover: freeze writes or use an explicitly tested dual-write/catch-up plan; take final backup; record version/checksum/count baseline; obtain owner sign-off.
  8. Execute and reconcile: run idempotent migration, compare counts/checksums and sample references, test critical user journeys, monitor errors; stop/restore if integrity thresholds fail.
  9. Close: archive migration report and approvals; delete temporary exports according to retention; monitor heightened alerts for at least 48 hours.

22.2 Environments and deployment

  • Maintain local/test, shared staging, and production as separate Supabase projects/environments. Never use production personal data in developer machines; use synthetic or approved masked data.
  • Use separate credentials per environment; service-role key only in server runtime/controlled migration pipeline; no credential in browser bundles or logs.
  • CI must run JavaScript lint/syntax/type checks applicable to the project, SQL parsing/lint where available, unit/integration tests, migration clean-install and upgrade tests, permission/RLS tests, dependency/security scan, and `git diff --check`.
  • Deploy additive schema changes first when backward compatible, then server code, then UI/feature flags. Destructive cleanup is a later release after old code is retired and data verified.
  • Use an expand/migrate/contract sequence: add nullable/new structures, dual-read or backfill if needed, validate, switch reads/writes, then remove old structures in a separate reviewed migration.
  • Production database migrations require named operator, approved change record, backup, maintenance/impact notice, pre/post checks, stop condition, and recovery owner.

22.3 Release go/no-go checklist

  • All baseline decisions affecting this release are accepted and recorded; unresolved issues have an explicit safe deferral.
  • Migration clean-install and upgrade rehearsal passed on representative schema; counts/data reconciliation approved; backup restore succeeded.
  • Critical user journeys and authorization matrix pass for every role/scope/module combination in the release.
  • No critical/high security defect remains; medium findings have written risk acceptance, mitigation, owner, and expiry.
  • Module readiness checks prevent enabling incomplete modules; pause/resume behavior is tested.
  • Monitoring, alert routing, incident contacts, support hours, rollback/forward fix, and release notes are ready.
  • HR/newsroom domain owners accept UAT; super-admin owner verifies setup; technical and security leads approve production deployment.
  • Post-release owner is on call; smoke tests, error/latency thresholds, and a 48-hour enhanced monitoring window are scheduled.
